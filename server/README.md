# 재고 할당 관리 — 실시간 공유 버전

기존에 드렸던 `재고_할당_관리.html`은 각자 파일을 내려받아 자기 컴퓨터에서 여는 방식이라, 다른 사람의 화면과 서로 연결되어 있지 않았습니다. 이 폴더는 그 도구를 **하나의 주소(URL)에 여러 사람이 동시에 접속해서, 한 명이 상품·로케이션·자동할당·검증 등을 바꾸면 다른 모든 사람 화면에 실시간으로 반영되도록** 만든 서버 버전입니다.

화면 구성, 자동 할당 로직, 까대기, 상품명 고정구역 규칙, PDA 검증, 일자별 입고 기록 등 기존 기능은 전부 동일합니다. 달라진 점은 데이터가 브라우저 메모리가 아니라 **서버 하나에 저장되고, Socket.IO로 실시간 방송**된다는 것뿐입니다.

**새로 추가된 기능 (2026-08-14)**
- **차수/업체명 태그**: 입고가 하루에 여러 번, 업체별로 들어올 때 구분할 수 있도록 «입고 · 자동할당»에 차수/업체명 선택 드롭다운이 추가됐습니다. 목록은 «설정 · 백업 → 차수/업체명 프리셋»에서 관리합니다. 자동 할당을 실행하면 그 배치의 모든 항목에 선택한 값이 태그되고, «할당 실행 이력 → 일자별 입고 기록»에서 년/월/일에 이어 차수/업체명으로도 걸러볼 수 있습니다.
- **CBM 요약 탭**: 보내주신 구글시트 "CBM(원본)의 사본"/노션 CBM 기록과 같은 구조로 층별 전체·사용·잔여 CBM/파레트를 보여주는 탭입니다. 전체 용량(1층 1,811·2층 2,148·3층 199자리, 파레트 1자리=2.12 CBM 고정)은 실제 창고 자료 기준 고정값이고, 사용량은 하단 "기록 추가" 폼에 입력한 날짜별 사용 Loc을 기준으로 계산됩니다. 과거 이력(2026년 1월~8월 초)은 보내주신 자료를 그대로 옮겨 미리 채워뒀고, 이후로는 이 화면에서 계속 새 날짜를 입력해 이어갈 수 있습니다. ⚠️ 이 도구에 현재 등록된 로케이션 수(1층 1,523·2층 1,634·3층 205자리)는 실제 창고 전체 자리수보다 적어서, "사용 Loc"은 자동 계산이 아니라 직접 입력하는 방식으로 만들었습니다 — 기존에 쓰시던 방식대로 실사/집계한 값을 입력해주세요.

**새로 추가된 기능 (2026-08-14, 2차)**
- **불량수량/불량로케이션 고정값**: «할당 실행 이력 → 일자별 입고 기록(엑셀 붙여넣기용)»에서 복사·CSV 내보내기 시 불량수량은 항상 `0`, 불량로케이션은 항상 `00-00-00-00`으로 통일해서 채웁니다. (박스번호는 이 도구에서 관리하지 않아 계속 빈 칸입니다.)
- **할당기록 로케이션 정정**: «할당기록 · 검증» 탭의 표에서 로케이션 옆 "수정" 버튼을 누르면 그 기록의 로케이션을 직접 고칠 수 있습니다. 자동 할당이 제안한 자리에 현장에서 이미 다른 물건이 있어 실제로는 다른 자리에 적치한 경우처럼, 기록만 바로잡아야 할 때 사용하세요. 수정 즉시 다른 접속자 화면에도 실시간으로 반영됩니다.

**새로 추가된 기능 (2026-08-18)**
- **자투리(부분수량) 1단 배치 — 필수 → 우선으로 완화**: 접근성 때문에 자투리 수량은 그동안 1단(tier 01) 로케이션에만 배치됐는데, 1단이 꽉 차 있으면 "공간 부족·배치된 위치 없음"으로 아예 배치를 포기했습니다. 이제는 1단을 **우선** 시도하되, 1단에 빈 자리가 없으면 자동으로 2·3·4단 등 다른 단의 빈 자리로 넘어가서 배치합니다(같은 구역 제한은 그대로 유지됩니다 — 예: 셀프시공 롤매트류는 여전히 1R-/1S- 구역 안에서만, 다만 1단이 아니어도 됨).
- **할당기록 수량 정정 · 기록 삭제**: «할당기록 · 검증» 표의 로케이션 칸에 있던 "수정" 버튼이 이제 **로케이션과 수량을 함께** 고칠 수 있게 바뀌었고, 옆에 "삭제" 버튼이 새로 생겼습니다. 중요한 점은 **기록만 바뀌는 게 아니라 실제 로케이션 재고도 같이 움직인다**는 것입니다.
  - 로케이션을 바꾸면 원래 자리는 비워지고 새 자리에 재고가 올라갑니다.
  - 수량을 바꾸면 그 자리의 실재고 수량도 같이 바뀝니다.
  - **수량을 줄이면 «남는 수량을 어디로 보낼지» 묻습니다.** 12개를 넣기로 했는데 실제로 5개만 들어갔다면 나머지 7개는 보통 다른 자리로 가기 때문입니다. 세 가지 중에 고르세요 — ①**자동으로 다른 빈 자리에 배치**(기본, 평소 자동할당과 같은 규칙으로 자리를 찾고 기록도 따로 남습니다) ②**직접 자리 지정**(어디에 넣었는지 알 때) ③**배치하지 않음**(반품·불량 등으로 재고에서 빼야 할 때). 자동 배치는 방금 줄인 그 자리로 다시 합짐되지 않도록 그 자리를 빼고 찾습니다.
  - 삭제하면 그 기록의 수량만큼 실재고에서 빠지고, 그 자리에 남는 수량이 없으면 다시 «빈 자리»가 되어 다음 자동할당에 쓰입니다. (합짐으로 한 자리에 기록이 여러 건 쌓여 있으면 해당 기록 몫만 빠집니다. 2PLT 상품이면 짝 슬롯도 함께 정리됩니다.)
  - 덕분에 «바코드로 적치 위치 찾기»와 «로케이션 현황»이 정정 후에도 항상 실제와 맞습니다. 삭제는 되돌릴 수 없어서 확인 창이 한 번 뜹니다.
- **바코드로 적치 위치 찾기**: «할당기록 · 검증» 탭 맨 위에 새 카드가 추가됐습니다. 상품 바코드를 스캔(또는 입력 후 Enter)하면 그 상품이 배정된 로케이션이 큼직하게 표시됩니다 — 예를 들어 `8809527904370` 바코드를 찍으면 배정된 `1R-08-03-01` 같은 위치가 바로 뜹니다. 같은 카드가 PDA 전용 화면(`/pda.html`)에도 그대로 있고, PDA에서는 글자를 더 크게 키워뒀습니다. 등록된 위치가 없는 바코드는 "등록된 로케이션이 없습니다"로 표시됩니다.

## 1. 로컬에서 먼저 확인해보기

```bash
cd server
npm install
npm start
```

`http://localhost:3000` 을 브라우저 두 개(또는 창 두 개)로 열어서, 한쪽에서 상품을 추가하거나 자동 할당을 실행하면 다른 쪽 화면에 몇백 ms 안에 자동으로 반영되는 것을 확인할 수 있습니다. 화면 우측 상단의 배지가 접속 상태(🟢 실시간 연결됨 · N명 접속)를 보여줍니다.

## 2. 인터넷에 올려서 여러 사람이 접속하게 하기 (무료: Render.com 추천)

로컬에서만 실행하면 같은 와이파이/네트워크에 있는 사람들끼리만 접속할 수 있습니다(`http://내PC의 IP:3000`). 사무실 밖에서도 접속하게 하려면 아래처럼 무료로 호스팅해두는 것을 추천합니다.

1. 이 `server` 폴더를 GitHub 저장소로 올립니다(비공개 저장소로 만들어도 됩니다).
2. [render.com](https://render.com) 에 가입 → **New +** → **Web Service** → 방금 만든 저장소를 연결합니다.
3. 폴더 안에 이미 넣어드린 `render.yaml` 덕분에 대부분 자동으로 설정됩니다. 수동으로 입력해야 한다면:
   - **Build Command**: `npm install`
   - **Start Command**: `node server.js`
   - **Plan**: Free
4. 배포가 끝나면 `https://프로젝트이름.onrender.com` 같은 주소가 생깁니다. 이 주소를 팀원들에게 공유하면, 각자 이 주소로 접속해서 실시간으로 같은 화면을 봅니다.

Railway.app, Fly.io 등 다른 Node.js 호스팅도 동일한 방식(빌드: `npm install`, 실행: `node server.js`)으로 사용할 수 있습니다.

## 3. 데이터는 어떻게 저장되나요? (중요 — 꼭 읽어주세요)

- 이 서버는 전체 상태(상품/로케이션/할당기록/규칙/실행이력/차수·업체명 프리셋/CBM 기록)를 저장소 하나에 통째로 저장합니다. 아래 7번 항목처럼 **Supabase(무료 외부 DB)를 연결하면 그쪽에 저장**되고, 연결하지 않으면 예전처럼 서버 안의 `data/state.json` 파일에 저장됩니다.
- **Supabase를 연결하지 않고 로컬 파일에만 저장하는 경우** — Render 무료 플랜은 "영구 디스크"를 제공하지 않기 때문에, **재배포뿐 아니라 15분 이상 접속이 없어서 서버가 잠들었다가 다시 깨어날 때도** `data/state.json`이 초기화되어 데이터가 사라집니다. 즉 점심시간이나 밤사이처럼 잠깐만 안 써도 그동안 입력한 내용이 사라질 수 있다는 뜻입니다. 실제 운영에 쓰시려면 아래 7번 항목대로 Supabase를 연결하시길 강력히 권장드립니다.
- 그 전까지는(또는 Supabase 연결 후에도 만약을 대비해) 설정 탭의 **"전체 백업 다운로드"**를 자주 눌러 JSON 백업을 로컬에 보관해두시길 권장합니다. 데이터가 사라지더라도 "백업 파일 불러오기"로 복원하면 됩니다(복원하면 접속한 모두에게 즉시 반영됩니다).
- **동시 편집 규칙**: 두 사람이 정확히 같은 순간에 서로 다른 내용을 저장하면, 나중에 서버에 도착한 저장이 이깁니다(가장 단순한 "마지막 저장이 이긴다" 방식). 실제 창고 운영처럼 한 번에 한 사람이 순서대로 작업하는 상황에서는 문제가 없지만, 여러 명이 정확히 동시에 같은 항목을 편집하는 경우까지 안전하게 병합해주진 않습니다.

## 4. 기존 "다운로드형 단독 파일" 버전과의 관계

`/home/claude/work/재고_할당_관리.html` (기존에 드린 파일)은 그대로 유지됩니다 — 인터넷 연결이나 서버 없이 혼자 오프라인으로 써야 할 때는 계속 그 파일을 쓰시면 됩니다. 이 `server` 폴더는 **여러 사람이 실시간으로 같이 봐야 할 때** 사용하는 별도 버전입니다. 화면과 기능은 동일하고, 데이터가 어디 저장되는지(브라우저 vs 서버)만 다릅니다.

## 5. (선택) 개발자용 회귀 테스트

`tests/` 폴더에 Playwright 기반 자동 테스트가 있습니다(실시간 동기화, 접속자 수, 전체 초기화, 백업 복원 등을 검증). 실행하려면 Playwright를 별도로 설치해야 합니다:

```bash
npm install -D playwright
npx playwright install chromium
node server.js &          # 서버를 먼저 띄운 뒤
node tests/test_realtime.js
node tests/test_persist.js
node tests/test_resetall.js
node tests/test_restore.js
node tests/test_batch_cbm.js
```

## 6. 기능을 추가했는데 이미 배포된 서버는 어떻게 되나요?

이번처럼 코드를 수정한 뒤에는, 이 `server` 폴더 내용을 그대로 GitHub 저장소에 다시 올리면(git push, 또는 웹에서 파일 업로드) Render가 자동으로 다시 빌드·배포합니다. Supabase를 연결해두셨다면 데이터는 그대로 유지되니 걱정 없이 재배포하시면 됩니다. 아직 로컬 파일로만 저장 중이라면, 3번 항목에서 설명한 대로 재배포 시 데이터가 초기화될 수 있으니 업데이트를 올리기 전에 꼭 설정 탭에서 **"전체 백업 다운로드"**로 최신 데이터를 받아두시고, 재배포가 끝난 뒤 필요하면 **"백업 파일 불러오기"**로 복원해주세요.

## 7. 무료로 데이터가 계속 유지되게 하기 (Supabase 연동)

앞서 설명한 것처럼, Render 무료 플랜은 15분 이상 접속이 없으면 서버가 잠들었다가 깨어날 때 로컬 파일이 초기화됩니다. 이 문제를 **비용 없이** 해결하려면, 무료 데이터베이스 서비스인 [Supabase](https://supabase.com)에 데이터를 저장하도록 연결하시면 됩니다. 서버 코드는 이미 Supabase를 지원하도록 만들어져 있고, 아래 환경변수 2개만 설정하면 자동으로 전환됩니다(설정하지 않으면 지금처럼 로컬 파일을 계속 씁니다).

1. **Supabase 가입 및 프로젝트 생성**: [supabase.com](https://supabase.com) 에서 무료로 가입하고 **New Project**로 새 프로젝트를 하나 만듭니다(리전은 서울/도쿄처럼 가까운 곳 추천, 데이터베이스 비밀번호는 아무 값이나 설정 후 잘 보관).

2. **테이블 만들기**: 프로젝트가 만들어지면 왼쪽 메뉴 **SQL Editor**를 열고 아래 SQL을 붙여넣어 실행(Run)합니다.
   ```sql
   create table app_state (
     id int primary key,
     data jsonb not null default '{}'::jsonb,
     updated_at timestamptz default now()
   );
   insert into app_state (id, data) values (1, '{}'::jsonb);
   ```

3. **키 확인**: 왼쪽 메뉴 **Project Settings → API**로 들어가서 두 가지를 복사해둡니다.
   - **Project URL** (예: `https://xxxxxxxx.supabase.co`)
   - **service_role** 비밀 키 (⚠️ `anon` 키가 아니라 `service_role` 키입니다 — 이 키는 절대 브라우저나 GitHub 공개 저장소에 노출되면 안 되고, 아래처럼 Render의 서버 환경변수로만 사용해야 합니다)

4. **Render에 환경변수 등록**: Render 대시보드 → 해당 서비스 → **Environment** 탭 → **Add Environment Variable**로 아래 2개를 추가합니다.
   - `SUPABASE_URL` = 2번에서 복사한 Project URL
   - `SUPABASE_SERVICE_KEY` = 2번에서 복사한 service_role 키
   - 저장하면 Render가 자동으로 재배포합니다.

5. **확인**: 재배포가 끝난 뒤 Render의 **Logs** 탭에서 `[store] Supabase에 데이터가 저장됩니다`라는 로그가 보이면 정상적으로 연결된 것입니다. 이제부터는 서버가 잠들었다가 깨어나도, 심지어 재배포를 하더라도 데이터(프리셋 포함)가 그대로 유지됩니다.

**참고**: Supabase 무료 플랜은 저장 용량 500MB까지 무료이고(이 도구는 현재 1MB 안팎이라 충분), 다만 **7일 동안 Supabase 프로젝트 자체에 아무 활동이 없으면 프로젝트가 일시정지**될 수 있습니다(데이터는 사라지지 않고, Supabase 대시보드에서 "Restore" 버튼 한 번만 누르면 다시 살아납니다). 창고에서 이 도구를 최소 일주일에 한 번이라도 쓰신다면 이 문제는 사실상 걱정하지 않으셔도 됩니다.
